# 캐시 데우기·파킹 비용 정책
## Rollover 확장 적용 연구 및 참조 구현 v1.0

**작성일: 2026-09-19 | 실측 기간: 2026-09-17~18 | lane: claude-sdk-oauth**

### 핵심 결정

**비용 교차점은 알림용으로, 앞으로의 기대비용은 실제 동작 결정용으로 사용한다.**

짧은 유휴에는 캐시를 잠시 유지하고, 다시 이어갈 긴 유휴에는 인수인계를 검토한다. 재개하지 않을 작업은 추가 요청 없이 만료시킨다. 현재 자료만으로 모든 세션에 적용할 최적의 고정 유휴시간은 정할 수 없다.

| 구분 | 확장에 넣을 규칙 |
|---|---|
| 비용 단위 | 입력 정가 환산 토큰. 실제 토큰 수·달러·OAuth quota와 구분 |
| 대표 파킹식 | P = 0.2 × C + 40,000 + 스킬 비용 + 시스템 캐시 만료 차액 |
| 교차점 | N* = ceil((P − 복귀 읽기 비용) / 데우기 1회 비용) |
| 실제 결정 | 지금부터의 데우기·파킹·만료 기대비용 중 최소값 선택 |
| 원문 보존 | 만료·파킹 모두 원래 대화와 작업 파일은 삭제하지 않음 |
| 실행 상태 | 계산 코드는 검증했지만 실제 rollover 저장소에는 미적용 |

### 대표 수치

C=150K, TTL=5분, 데우기 간격=4분 30초, 공유 시스템 캐시 유지, 스킬 재주입 없음이면 데우기 1회는 15K, 부모 인수인계는 약 45K, 후속 복원은 약 25K다. 파킹 총액은 약 70K이며, 처음부터의 전략 비교에서 4번째 데우기 직후인 18분에 교차한다.

**이 18분은 자동 파킹 명령이 아니다.** 이미 20분을 데웠어도 지금부터 2분 뒤 돌아올 예정이면 추가 데우기가 유리할 수 있다. 이미 쓴 비용은 실제 선택식에 더하지 않는다.

### 범위와 증거 수준

사용자 제공 집계는 관측으로 표시했다. 원본 로그를 재분석하지는 않았다. 비용식과 시뮬레이션은 그 집계에 근거한 추론이며, 40K 고정비는 대표 초기값이지 통계적으로 적합한 회귀계수가 아니다. 아래 검증은 계산의 일관성을 검증하며 실제 비용 절감률이나 요약 품질을 입증하지 않는다.

# 1. 실측과 초기 파라미터

### 1.1 사용자 제공 집계 [U1, U2]

| 항목 | 보고값 | 적용 시 주의 |
|---|---|---|
| 일반 인수인계 문서 | 평균 6,279 bytes; 약 1.5~1.8K 토큰 추정 | 전체 rollover 유형 혼합. tokenizer 실측 아님 |
| 유휴 파킹 문서 H | 5건 평균 약 1.2K 토큰, 4.7KB | 예산 초과 rollover 약 1.7K와 분리 |
| 후속 시스템 입력 S | 약 27.5K 중 25K 캐시 히트 | 보고된 비용 2.7K는 집계 범위 확인 필요 |
| 후속 복원 순비용 | 평균 약 20K, 범위 9.5~27K 환산 | 문서 3~5K보다 반복 읽기·라운드 비용이 큼 |
| 스킬 재주입 | 해당 시 약 +11K 환산 | 복원 총액에 이미 포함됐다면 다시 더하지 않음 |
| 부모 인수인계 생성 | 약 40~55K 환산 | C=110~190K를 warm으로 약 2회 읽고 출력 약 3K |
| 파킹 총비용 | warm 전환에서 약 65~90K 환산 | 장기 유휴 후 실제 복귀까지 측정한 값인지 확인 |

### 1.2 산술·집계 보정

27.5K 중 25K를 0.1배로 읽고 나머지 2.5K를 정가로 읽으면 5.0K다. 나머지가 1.25배 쓰기라면 5.625K다. 2.7K는 거의 전부 캐시 히트일 때의 값에 가깝다. 별도 항목에 포함된 부분인지 확인하기 전에는 총비용에 차액을 자동 추가하지 않는다.

참조 구현의 후속 복원 초기값 25K는 복원 20K와 시작 비용 약 5K를 묶은 대표값이다. 실제 요청을 중복 없이 합산한 값이 확보되면 이 초기값을 교체한다.

### 1.3 계수와 단위

| 변수 | 초기값 | 성격 |
|---|---:|---|
| 캐시 읽기 r | 0.1 | 이번 연구의 가중치. 모든 모델·quota에 보편 적용하지 않음 |
| 비캐시 입력 / 5분 쓰기 / 1시간 쓰기 | 1 / 1.25 / 2 | API 가격 구조 참고 [R1] |
| 모델 출력 o | 5 | 사용자 환산 가중치 |
| 부모 전체 컨텍스트 읽기 m | 2회 | 사용자 관측에 따른 대표값 |
| 부모 청구 모델 출력 O | 약 3,000토큰 | 문서 H와 별도 |
| 후속 복원 D0 | 25,000 환산 토큰 | 대표 초기값. 스킬 미포함 |
| 데우기 간격 δ | TTL의 90% | 안전 여유를 둔 설계값, 경제적으로 최적이라는 근거 없음 |

이후 C와 비용은 코드에서 토큰 단위, 시간은 밀리초 단위로 저장한다. 표에서만 K와 분으로 표시한다.

# 2. 비용 공식

### 2.1 실제 청구량을 우선한다

```text
E = input × 1 + write5m × 1.25 + write1h × 2
    + cacheRead × 0.1 + modelOutput × 5
```

각 항목은 겹치지 않아야 한다. tool_result 텍스트는 다음 요청의 입력이며, 모델 출력 가격을 적용하는 대상이 아니다. [R3] compaction의 usage.iterations가 있다면 iteration들을 합산하되, 같은 내용을 나타내는 최상위 합계를 다시 더하지 않는다. [R2]

### 2.2 부모 생성과 미래 복원을 분리한다

```text
A = r × C                       // 기존 세션의 실제 복귀 읽기
w = r × C + ε                   // 데우기 한 번; ε는 부가 입력·출력·쓰기
G = m × r × C + o × O + 기타     // 지금 지불하는 부모 인수인계 비용
D = D0 + 11,000 × I + ΔS         // 복귀할 때만 지불하는 후속 복원 비용
P = G + D                       // 복귀가 발생한 파킹 1회의 총비용
```

I는 스킬 재주입이 있으면 1, 없으면 0이다. 대표 초기값을 넣으면 G≈0.2C+15,000, D≈25,000+11,000I+ΔS, 따라서 P≈0.2C+40,000+11,000I+ΔS다. H가 D 또는 실제 생성 비용에 이미 들어 있다면 다시 더하지 않는다.

이 식은 후속 세션을 실제 복귀 때 시작하는 파킹을 전제로 한다. 파킹 직후 후속 세션까지 실행했다면 그 비용은 미래 D가 아니라 이미 발생하는 비용이다. 이후 다시 만료된 후속 컨텍스트를 읽는 비용도 추가해야 한다.

### 2.3 시스템 캐시 만료와 cold 비용

a를 재쓰기 배수, S_hit를 유지되는 공유 prefix로 둔다.

```text
ΔS = (a − r) × 만료된 공유 prefix 토큰 수
F_shared = r × S_hit + a × (C − S_hit)
F_full = a × C
```

150K, S_hit=25K, r=0.1, a=1.25이면 F_shared=158.75K, F_full=187.5K, 공유 prefix 25K의 만료 차액은 28.75K다. 새 입력을 캐시에 쓰지 않는 경로라면 그 부분에는 a=1을 적용한다. 파킹과 cold에 서로 다른 청구 범위를 적용하지 않는다.

전체가 아직 warm일 때 그냥 두고 복귀하면 비용은 F가 아니라 A다. 공유 prefix 생존은 동일한 텍스트라는 이유만으로 가정하지 말고 실제 캐시 재사용 근거가 있어야 한다. [R1]

# 3. 비용 교차점과 유휴시간

### 3.1 계산식

```text
W(N) = A + N × w
N* = max(0, ceil((P − A) / w))
t* = 첫 데우기 예정시각 + (N* − 1) × δ   // N* >= 1일 때
```

유휴 시작에 TTL이 온전히 남았고 첫 데우기를 δ 뒤에 하면 t*=N*δ다. 대표식에서는 다음처럼 쓸 수 있다.

```text
N* = ceil(1 + (40,000 + 11,000I + ΔS) / (0.1C))
t* = 0.9 × TTL × N*
```

이는 처음부터 데운 전략과 처음부터 파킹한 전략의 비교다. 이미 쓴 데우기 비용을 회수할 수 있다는 뜻이 아니다. w=0이고 P>A이면 유한한 교차점은 없다.

### 3.2 기본 조건의 참고표

| C | P | TTL 5분 | TTL 30분 | TTL 1시간 |
|---:|---:|---:|---:|---:|
| 50K | 50K | 40분 30초 | 4시간 3분 | 8시간 6분 |
| 100K | 60K | 22분 30초 | 2시간 15분 | 4시간 30분 |
| 150K | 70K | 18분 | 1시간 48분 | 3시간 36분 |
| 200K | 80K | 13분 30초 | 1시간 21분 | 2시간 42분 |
| 300K | 100K | 13분 30초 | 1시간 21분 | 2시간 42분 |
| 500K | 140K | 9분 | 54분 | 1시간 48분 |

공유 시스템 캐시 유지·스킬 재주입 없음·P 고정 조건이다. C=110~190K 밖은 외삽이다. 30분은 다른 lane에 대한 가상 TTL이며 Claude의 네이티브 30분 옵션을 뜻하지 않는다. 1시간 행도 TTL만 바꾼 참고값으로, 그 lane의 실제 쓰기·복원 비용이 확보되면 보정한다.

### 3.3 만료 선택과 시계 경계

C=50K에서 S_hit=25K라면 cold 비용 33.75K는 파킹 50K보다 싸다. 따라서 표의 교차시간에 도달해도 파킹을 선택할 이유가 없다.

사용자 복귀와 타이머가 정확히 겹치면 사용자 요청이 우선하고 데우기를 취소한다. 표의 시간은 해당 타이머가 실제 실행된 직후의 경계다. 실제 복귀까지 데우는 횟수는 다음처럼 계산한다.

```text
N(T) = #{ d0 + jδ < T : j = 0, 1, ... }
     = max(0, ceil((T − d0) / δ))
```

d0는 지금부터 첫 데우기까지의 시간이다. C=150K·5분 TTL에서 스킬만 추가하면 교차 22분 30초, 공유 prefix 25K만 재쓰면 27분, 둘 다 있으면 31분 30초다.

# 4. 실제 자동 선택: 앞으로의 기대비용

### 4.1 세션 크기·유휴시간·TTL만으로는 부족하다

같은 C와 TTL이고 현재까지 똑같이 20분을 쉬었어도, 다음 요청이 2분 뒤인지 내일인지 영원히 없는지에 따라 선택이 달라진다. 현재 유휴시간은 앞으로의 복귀 분포를 갱신하는 정보로 사용한다. 이미 지불한 비용을 최소화식에 다시 넣지 않는다.

T를 실제 복귀 시각으로, t를 현재 판단 시각으로 둔다. 복귀하지 않는 경우도 확률에 포함한다. 아래 기대값은 지금까지 부재했다는 조건하에서 계산한다.

```text
J_park(t) = G(t) + E[복귀한 경우의 D(T,t)]
J_expire(t) = E[복귀한 경우의 원문 재개 비용 F(T,t)]
J_warm(t) = w(t) + q(t) × A(t) + (1 − q(t)) × V(t + δ)
V(t) = min(J_park(t), J_expire(t), J_warm(t))
```

q(t)는 다음 판단 시각까지 돌아올 확률이다. F(T,t)는 현재 캐시 만료 전 복귀하면 A, 이후이면 해당 시점의 cold 비용이다. D에는 공유 prefix 만료, 스킬, 복원 입력·출력 등을 포함한다. 복귀가 없으면 D와 F는 발생하지 않지만 G는 발생한다.

참조 구현은 복귀 시각별 확률 목록을 뒤에서부터 계산하는 동적 계획법을 사용한다. **고정 lane·고정 C·정해진 판단 간격·주어진 복귀 분포·원자적인 비용 처리라는 모델 안에서의 최소값**이다. 실제 세계 전체에 대한 최적성 보장은 아니다.

### 4.2 검증용 가상 시나리오

현재 TTL이 30초 남은 150K 세션, 공유 prefix 유지, w=A=15K, G=45K, D=25K의 예다. 확률은 사용자의 실제 측정값이 아니라 코드 검증용 입력이다.

| 앞으로의 복귀 조건 | 선택 | 기대 비용 |
|---|---|---:|
| 20초 뒤 100% 복귀 | 추가 요청 없이 대기/만료 허용 | 15K |
| 2분 뒤 100% 복귀 | 한 번 데우기 | 30K |
| 12분 뒤 100% 복귀 | 데우기 후 재평가 | 60K |
| 1시간 뒤 100% 복귀 | 지금 파킹 | 70K |
| 다시 재개하지 않음 100% | 만료 허용 | 0 |
| 1시간 뒤 10%, 미복귀 90% | 만료 허용 | 15.875K |
| 2분 뒤 90%, 1시간 뒤 10% | 데우기 후 재평가 | 35.5K |

### 4.3 확률도 수치로 비교할 수 있다

복귀 시점이 현재 만료 이후이고 cold 비용 F가 일정하다면, 최종 복귀 확률 p에 대해 파킹은 G+pD, 만료는 pF다. F>D일 때 파킹이 더 저렴할 조건은 p>G/(F−D)다. 대표 예에서는 45/(158.75−25)=33.6%다. 만료 전에 돌아올 확률까지 있으면 위 전체식을 사용한다.

# 5. 확장 제어와 안전장치

### 5.1 두 시계를 구분한다

| 필드 | 갱신 사건 |
|---|---|
| lastMeaningfulActivityAt | 실제 사용자 입력·실제 작업 활동 |
| lastVerifiedCacheRequestStartedAt | 캐시 읽기/쓰기가 확인된 요청의 시작 |
| cacheExpiresAt | prefix별 요청 시작 + 확인한 TTL |
| sessionGeneration / laneKey | 실제 세션 교체·lane/model/effort/prefix 변경 |

데우기로 첫 번째 시계를 갱신하지 않는다. 그러면 가짜 요청이 유휴를 계속 초기화해 무한 유지가 된다. TTL은 응답 완료가 아니라 요청 시작부터 계산한다. [R1]

```text
lead = max(0.1 × TTL, 요청 도착 지연 + 타이머 지터 + 안전 여유)
δ = TTL − lead
nextDecisionAt = cacheExpiresAt − lead
```

lead가 TTL 이상이면 해당 방식의 warm 유지가 안전하지 않다. 두 번째 부모 호출이 첫 호출의 갱신 TTL 밖에서 시작하면 0.2C 가정도 깨지므로, 각 요청의 hit/write를 따로 측정한다.

### 5.2 실행 순서

```text
사용자 요청 / 모델 / 도구 작업 중이면 비용 판단보다 실제 작업을 우선
→ 만료 전 판단 시각까지는 추가 요청 없이 대기
→ 유효 캐시와 lane을 확인
→ 현재 비용 스냅샷과 조건부 복귀 분포를 계산
→ 미래 기대비용 최소 행동을 선택
→ 실행 직전에 sessionGeneration과 사용자 대기를 다시 확인
→ 부모 원문 보존, handoff 파일 검증·원자적 전환, 결과 계측
```

요약 생성 중 사용자가 돌아오면 정책에 따라 취소 또는 대기시킨다. 이미 발생한 출력 비용은 지워지지 않는다. 실패한 handoff로 활성 세션을 교체하지 않는다. 처음 적용할 때는 shadow 모드로 판단만 기록하고, 실제 요청·전환은 호출 측에서 별도 허용한다.

### 5.3 복귀 예측 자료가 없는 초기 운영

확률이 없다고 임의로 50%나 100%를 넣지 않는다. 참조 구현은 이 경우 자동 파킹하지 않고 기본적으로 만료를 허용한다. 일정 비용의 기다림을 승인할 경우 별도 예산 규칙을 사용할 수 있다.

```text
B_guard = max(0, min(P_reference, F_reference) − A)
이미 쓴 데우기 비용 + 다음 데우기 비용 < B_guard 일 때만 추가 데우기
그 밖에는 LET_EXPIRE; 이것만으로 PARK를 지시하지 않는다.
```

150K·공유 prefix 유지 예에서는 B_guard=55K다. 15K짜리 데우기를 최대 3회 허용하고, 다음 예정 시각인 18분에는 추가 결제를 중단한다. 이는 낭비 상한을 정하는 휴리스틱이지 비용 최적화 증명이 아니다. 예측이 없으면 이 유예 자체도 낭비일 수 있다.

# 6. 계측·보정 명세

### 6.1 비용을 작업 단계별로 기록한다

| 단계 | 기록 범위 |
|---|---|
| warm | 유휴 갱신 요청의 모든 모델 호출과 실제 청구량 |
| park_parent | 파킹 지시부터 handoff 저장·검증 종료까지 |
| restore_child | 실제 복귀 후 후속 세션 시작부터 합의한 복원 종료점까지 |
| resume_raw | 만료 후 원문으로 재개한 동일 비교 범위 |
| first_useful_action | 첫 토큰이 아니라 실제 작업 재개까지의 지연 |

복원 종료점은 예를 들어 필요한 상태·파일 파악을 마치고 첫 본 작업 명령을 시작하는 지점으로 일관되게 정한다. 원문 재개와 후속 복원 양쪽의 공통 본 작업을 중복해서 비용 차이로 세지 않는다.

```text
requestId, sessionId, sessionGeneration, phase, laneKey
requestStartedAt, responseEndedAt, ttlMs, cachedPrefixTokens
uncachedInput, cacheWrite5m, cacheWrite1h, cacheRead, billedModelOutput
handoffTokens, restoreRounds, skillReinjected, sharedPrefixHitTokens
actualReturnGap, rightCensored, firstUsefulActionLatencyMs
```

API 이벤트의 증가분과 최종 누적값을 동시에 더하지 않는다. compaction iteration도 요청 단위로 중복 제거한다. [R2] byte/4 환산은 문서 크기 추정에만 쓰고 청구 비용은 usage로 확인한다. 토큰 카운팅 API도 실제 사용량과 소폭 다를 수 있다. [R4]

### 6.2 비용 모델 갱신

m=2를 우선 고정하고, 각 파킹의 측정 총비용에서 2rC와 명시된 스킬·만료 차액을 뺀 잔차를 관측한다. 이 잔차의 중앙값·평균·범위를 각각 보관한다. 표본 5건에서 기울기까지 자유롭게 적합하거나 신뢰구간을 확정하지 않는다.

실제 선택에서는 낮은 복원비와 높은 복원비를 대입한 결과도 비교할 수 있다. 비용 범위 양끝에서 같은 행동이 나오면 두 시나리오에서 선택이 일치한다고 기록한다. 범위 전체의 최적성이나 통계적 신뢰구간을 뜻하지 않는다. 결과가 바뀌면 shadow 유지 또는 명시적 예산 정책을 적용한다.

### 6.3 복귀 분포와 검열

마지막 메시지 유형·시간대·작업 상태별 과거 gap을 후보 특징으로 사용한다. 예측은 로컬 통계로 계산할 수 있으며, 판단할 때마다 LLM 호출을 추가할 필요는 없다.

```text
P(t+u1 < T <= t+u2 | T>t, x)
  = [F_gap(t+u2 | x) − F_gap(t+u1 | x)] / [1 − F_gap(t | x)]
```

F_gap은 전체 복귀 gap의 누적분포다. 아직 돌아오지 않은 진행 중 세션은 ‘영원히 미복귀’가 아니라 오른쪽 검열 자료다. 예측 기간 밖의 장기 복귀 꼬리도 0원으로 버리지 않는다. 제공 코드의 neverReturnsProbability는 진짜 미재개 확률이며, 임의의 8시간 cutoff를 뜻하지 않는다.

### 7.1 압축 품질은 별도 조건이다

비용이 같다고 같은 정보를 유지하는 것은 아니다. 중요한 제약과 미완료 상태가 보존되지 않는 작업은 allowParking=false로 파킹 후보에서 제외한다. 손실을 비용화한다면 복귀 1회당 품질 손실 L을 D에 더한다. L=0 초기값은 ‘손실이 없다’는 관측이 아니라 토큰 비용만 비교한다는 뜻이다.

### 7.3 실무 최적화와 사용자 체감

현재 실측에서는 부모의 두 번째 전체 읽기와 후속 복원 라운드가 큰 비용 항목이다. 절차상 불필요한 모델 호출을 하네스 검증으로 대체할 수 있는지 먼저 검토한다. 무조건 H를 줄이면 재검색이 늘 수 있다.

지연을 반영할 때는 ‘첫 토큰’뿐 아니라 ‘다시 유용한 작업을 시작하기까지’를 측정한다. 가치 환산이 가능하면 각 행동 비용에 대기시간×시간가치를 추가한다. 현재 로그로 200K cold 지연이나 품질 손실의 금액을 확정하지 않았다. 추가 미래 작업 턴에서 문맥 축소가 절약하는 비용도 현재 1회 재개 비교에는 포함하지 않았다.

# 8. 참조 구현과 검증

### 8.1 모듈 경계

| 함수 | 역할 |
|---|---|
| equivalentCost | 실제 usage를 중복 없는 환산 비용으로 변환 |
| baselineCosts | 이번 실측 기반 대표 비용 스냅샷 생성 |
| crossover | 크기·TTL별 최초 비용 교차점. 알림·표시 전용 |
| warmCallsBeforeReturn | 정확한 타이머 경계를 반영한 호출 횟수 |
| planIdle | 조건부 복귀 시나리오에 대한 미래 기대비용 최소화 |
| advise | 유휴·유효 캐시·사용자 요청 우선 등 실행 전 가드 |
| budgetFallback | 예측 부재 시 별도 승인한 유한 대기 예산 |

런타임 비용 단위는 토큰, 시간 단위는 밀리초다. 코드에 K단위로 값을 넣으면 1,000배 오류가 난다. TypeScript는 순수 함수이며 네트워크 요청·파일 삭제·실제 세션 전환을 수행하지 않는다.

### 8.2 확장 어댑터에서 구현할 것

원본 rollover 소스는 제공되지 않았으므로 해당 저장소에 대한 패치를 만들지 않았다. 어댑터는 실제 usage·TTL·prefix identity를 수집하고, sessionGeneration을 원자적으로 검사한 뒤 반환된 행동을 실행해야 한다. shadow/enforce 전환과 원문 보존·파일 쓰기 검증도 어댑터 책임이다.

서로 다른 TTL prefix가 섞이면 구간별 생존·가격을 적용해야 한다. API는 혼합 TTL을 지원하지만 [R1], 참조 계산기 한 번은 하나의 유효 TTL과 공유 캐시 생존 시나리오를 가정한다. lane이 바뀌면 새 스냅샷으로 다시 계산한다. `sharedCachePersists=true`는 미래 내내 외부 사용으로 공유 prefix가 유지된다는 강한 가정이다. 미확인 시 false로 계산하되 그 결과가 보수적 추정임을 기록한다.

### 8.3 테스트 결과

**30개 테스트 통과.** 그중 한 테스트는 120개의 재현 가능한 확률 시나리오를 생성해 동적 계획법 결과와 별도 재귀 계산의 결과를 대조한다. 캐시 크기 6개×TTL 3개의 교차 직전·직후도 검사했다.

검증 항목: 사용자 요청과 타이머 동시 발생, 잔여 TTL, 공유 캐시 만료, 스킬 재주입, 미복귀, cold가 파킹보다 저렴한 작은 세션, 품질 게이트, 확률 합계 오류, 0원 데우기, 매몰비용 배제, 예측 없는 자동 파킹 방지.

```text
Node.js 22.16.0 / TypeScript 5.8.3
node --test tests/cache-policy.test.cjs
30 tests / 30 pass / 0 fail
```

실제 provider 응답과 race condition, 복귀 예측 정확도, 비용 절감률, handoff 후 업무 성공률은 통합 실험으로 따로 검증해야 한다. API 가격 환산이 OAuth 구독 quota와 같은 상대 가중치로 차감된다는 점도 현재는 확인되지 않았다.
