# 캐시 데우기·파킹 정책 비교 검토
## 기존 rollover 정책 v1과 Claude의 Opus 5 / Fable 5.1 제안

작성: 2026-09-19

## 0. 결론

비용 모델의 골격은 같다. 기존 v1도 부모 인수인계 생성 G와 복귀 시 복원 D를 분리하고, 미복귀 확률과 정보 손실을 고려했다. 새 제안의 실질적인 확장은 모델별 quota 가중치와 복귀 후 컨텍스트 축소 절감 V다. 이 두 가지는 도입할 가치가 있다.

그러나 새 결정 절차를 그대로 배포해서는 안 된다. Fable 출력 가격 가정이 공식 표와 다르고, 현재의 최선 대안을 고정한 h 임계값은 다음 시점에 대안이 바뀌는 경우를 놓친다. 감소하는 복귀 hazard에서도 반례가 있다. 또한 미복귀가 허용되는 이 문제에는 제시한 ski-rental 2배 보장을 적용할 수 없다.

권고: 모델별 비용 계층은 보강하고, 기존의 미래 기대비용 동적 계획법은 유지한다. V는 공통 작업 구간을 정의한 뒤 추가한다. 기존 파일과 배포 동작은 이번 검토에서 수정하지 않았다.

### 증거 구분

- 사용자 제공 자료: 읽기/쓰기 quota 비율, 핑 주기, 파킹·복원 구조. 원시 quota 로그를 이번 검토에서 재집계하지 않았다.
- 공식 확인: 2026-09-19 Anthropic API 가격과 캐시 TTL 규칙. OAuth quota와 API 달러 가격은 별도다.
- 계산 검증: 아래 비용과 반례는 제공한 값을 대입해 직접 계산했다.
- 가상 반례: 실제 사용자의 복귀 습관이 아니라, 일반적인 최적성 주장을 검증하기 위해 구성한 확률 분포다.

## 2. 가격과 quota 상수

### 2.1 공식 API 가격 확인

단위는 USD / 1M tokens다. [A1, A2]

| 모델 | 비캐시 입력 | 5분 쓰기 | 1시간 쓰기 | 캐시 읽기 | 출력 |
|---|---:|---:|---:|---:|---:|
| Opus 5 | 5 | 6.25 | 10 | 0.50 | 25 |
| Fable 5.1 | 10 | 12.50 | 20 | 0.25 | 50 |

따라서 1시간 쓰기를 1로 정규화하면 API 가격상 Opus의 읽기/쓰기는 0.05, 출력/쓰기는 2.5다. Fable의 읽기/쓰기는 0.0125, 출력/쓰기는 2.5다.

사용자 자료의 읽기/쓰기 quota 비율 0.055와 0.022(대안 0.0165)는 별도 실측으로 취급한다. API 비율과 다르다고 실측을 폐기하지 않는다. 반대로 이 비율이 관측되었다는 이유로 모든 출력의 quota까지 API 가격에 비례한다고 확정할 수도 없다. 새 자료 자체가 출력 비율은 미측정이라고 명시한다.

Fable의 출력/쓰기 1.25는 '가격표 가정'으로는 잘못됐다. 공식 API 가격을 가정하려면 50/20=2.5를 사용한다. 실제 OAuth 출력 실측이 확보되면 그 값으로 대체한다.

5분 lane에서 읽기/쓰기 0.08은 Opus의 API 가격에 해당한다. Fable 5.1의 API 비율은 0.25/12.5=0.02다. 두 모델의 출력/5분 쓰기 비율은 4다.

### 2.2 같은 배수는 언제 약분되는가

모든 비용 항목에 동일한 양의 계수 k가 적용되고 같은 quota 목적함수를 최소화한다면 argmin(kJ)=argmin(J)이므로 약분 가능하다. 단위 변경도 같은 성질을 가진다.

다음은 별도 처리해야 한다.

- 부모와 후속 세션의 모델/lane이 다름.
- 5분 쓰기, 1시간 쓰기, 일반 입력이 혼합됨.
- 서로 다른 quota 제한이나 리셋 전후 자원 가치를 함께 고려함.
- 정보 손실·대기시간을 비용화하면서 같은 환산을 적용하지 않음.

공식 도움말은 사용량에 모델, 컨텍스트, 도구, effort 등이 영향을 준다고 설명하지만, 여기서 제시한 정확한 선형 OAuth 계수를 보장하지 않는다. [A3]

확장의 계측 원형은 다음처럼 보존하는 것이 낫다.

```text
Q = k_input*input + k_write5*write5 + k_write60*write60
    + k_read*cacheRead + k_output*billedModelOutput
```

실측 계수와 API 기본 계수는 출처 필드를 달리하고, 모델·lane·적용 시점을 키로 관리한다. 이미 환산된 D=25K, 스킬=11K를 단위 변경 없이 재사용하면 안 된다.

Fable 수정열은 읽기의 보고된 quota 비율은 유지하고, 미측정 출력에 대한 가격표 가정만 고친 혼합 시나리오다. 완전히 실측한 quota 결론은 아니다.

### 3.1 교차 시각과 실제 전환 시각의 구별

복귀 읽기 A와 핑 a가 같다면:

```text
N_cross = max(0, ceil((P - A)/a))
t_cross = firstPingDue + (N_cross-1)*Δ
```

첫 핑을 유휴 시작 후 Δ에 한다면 t_cross=N_cross*Δ다.

| 조건 | P/a | 교차 핑 횟수 | 핑 간격 | 비용 교차 시각 |
|---|---:|---:|---:|---:|
| 기존 v1의 1시간 TTL 참고 시나리오 | 4.667 | 4 | 54분 | 3시간 36분 |
| Opus 현재 | 4.939 | 4 | 55분 | 3시간 40분 |
| Opus 개선 가정 | 2.827 | 2 | 55분 | 1시간 50분 |
| Fable 원안 | 6.712 | 6 | 55분 | 5시간 30분 |
| Fable 출력 가정 수정 | 7.848 | 7 | 55분 | 6시간 25분 |

기존 v1의 1시간 행은 실제 1시간 lane 비용 검증이 아니라 TTL만 바꾼 참고값이라고 원문에 명시되어 있다. 위 비교는 큰 차이가 있는지를 보여주는 기준선이지 가격 실측 동등성의 증거가 아니다.

새 원안의 'n회까지 핑한 뒤 다음 마감에서 파킹'을 실행한다면, 전환은 (n+1)Δ다. 예를 들어 Opus의 4회 핑 누적은 3시간 40분이고, 그 뒤 다음 판단에서 파킹하는 시각은 4시간 35분이다. 핑 횟수, 비용 교차점, 실제 파킹 타이머를 같은 값으로 표시하지 않는다.

## 4. q 임계값은 기존 식과 같은 구조다

V와 Λ를 복귀 1회당 조건부 값으로 정의하고 D=B-V+Λ라 두면:

```text
J_park = G + qD
J_expire = qK
q* = G/(K-D)
```

분모가 양수일 때 q>q*이면 파킹이 만료보다 싸다. 분모가 0 이하이거나 q*가 1보다 크면 별도의 동률/경계 처리를 제외하고 파킹하지 않는다. 모든 복귀가 현재 캐시 만료 이후라는 단순화이며, 만료 전 복귀에는 K 대신 warm 재개 비용을 적용한다.

K=C는 전체 C가 실제로 다시 쓰일 때만 맞다. 공유 prefix Sh가 원문 재개에서도 살아 있으면 K_shared=ρr Sh+(C-Sh)다. Opus의 Sh=25K라면 K_shared=126.375K이고 q*=21.89%로 바뀐다. 두 경로 모두 Sh가 사라지는 상황이면 B에도 (1-ρr)Sh를 더해야 한다.

파킹 생성이 공유 prefix의 TTL을 갱신해서 그 경로만 cache hit가 나는 시간대는 가능하다. 따라서 무조건 같은 hit를 강제하는 것이 아니라, 실제 요청 시각별 생존 상태로 양쪽을 계산한다.

## 5. 단일 h 임계값의 정확한 한계

실패율 0, A=a, 비용 고정, 만료 직전이라는 조건에서 한 번 더 데우고 이후에도 같은 대안을 실행하기로 고정하면, 원안의 h*=a/(W-a)는 맞다. q<1이라는 이유만으로 이 식 자체가 틀리는 것은 아니다.

문제는 현재 선택한 대안을 다음 시점에도 고정하는 전체 절차다. 다음 구간에도 사용자가 돌아오지 않으면 q가 내려가고, 지금은 파킹이었던 최선 대안이 그때는 만료로 바뀔 수 있다.

### 5.1 감소 hazard에서도 발생하는 반례

Opus의 a=8.25, G=24, B=16.75, K=150을 그대로 사용한다. 현재 TTL은 거의 끝났고, 실패·스킬·V·Λ는 없다.

| 복귀 구간 | 현재 시점에서의 확률 |
|---|---:|
| 다음 55분 | 10% |
| 그 다음 55분 | 5% |
| 세 번째 55분 | 3% |
| 네 번째 55분 | 2% |
| 이 작업을 재개하지 않음 | 80% |

현재 q=20%, h=10%다. 조건부 구간 복귀 확률은 10%, 5.556%, 3.529%, 2.439%로 감소한다.

원안은 q>18.01%이므로 파킹을 대안으로 정하고, h<25.38%이므로 지금 파킹한다.

직접 계산하면:

```text
지금 파킹 = 24 + 0.20*16.75 = 27.350K
지금 만료 = 0.20*150 = 30.000K
한 번 핑 후 계속 부재하면 만료
  = 8.25 + 0.10*8.25 + 0.10*150 = 24.075K
```

한 번 더 데우는 쪽이 원안의 선택보다 약 12.0% 저렴하다. 다음 시점의 q는 0.10/0.90=11.11%로, 파킹 임계값 아래다. 즉 '일단 기다린 후 파킹을 안 할 자유'에 가치가 있다.

이 반례는 감소 hazard라는 전제까지 만족한다. 따라서 그 전제만으로 제시한 전체 절차의 최적 정지를 보장할 수 없다. 기존 v1 planIdle에 같은 비용과 분포를 넣으면 KEEP_WARM, 기대비용 24.075K를 반환한다.

### 5.2 한 단계 규칙을 유지하려면 최소 네 비용을 비교한다

0<=h<=q<=1, 다음 마감까지의 복귀 비용 A, 실패 없음, 비용 고정, 현재 유효 TTL 잔여분을 무시할 수 있는 경우:

```text
D = B - V + Λ
J_park_now         = G + qD
J_expire_now       = qK
J_warm_then_park   = a + hA + (1-h)G + (q-h)D
J_warm_then_expire = a + hA + (q-h)K
```

이 네 식의 최소값을 비교하면 위 반례는 해결된다. 그러나 두 구간 이상 계속 데울 선택까지 고려한 보편적 최적성은 여전히 없다. 기존 동적 계획법이 이미 있으므로 이를 유지하는 것이 더 일관적이다.

실패율을 (1-ρf)로 단순히 나누는 형태 역시 실패 시 즉시 대안의 비용과 상태가 보존된다는 등 추가 가정이 필요하다. 실제 실패·캐시 재쓰기·모델 전환은 상태 전이로 분리하는 것이 안전하다.

## 6. '최악에도 2배' 보장은 이 문제에서 성립하지 않는다

전통적 ski-rental에는 2-competitive 결정적 정책이 있다. [T1] 그러나 이 문제에는 '끝내 돌아오지 않으면 아무것도 하지 않아도 비용 0'인 경로가 존재한다.

예측이 없어 q=1로 놓고 Opus에 원안 규칙을 실행했는데 실제로 돌아오지 않는다면:

```text
원안: 핑 4회 + 부모 파킹 생성 = 4*8.25 + 24 = 57K
사후 최적: 아무것도 하지 않음 = 0
```

57K <= 2*0은 거짓이다. 사용자가 돌아오지 않아 B를 지불하지 않는다는 점까지 반영한 반례다. 이 연구처럼 유휴 시작 이전의 이미 쓴 비용을 제외한 추가 비용 기준에서는 유한한 곱셈 경쟁비 보장을 주장할 수 없다.

기존 v1의 예산 제한도 최적성/2배 보장이 없는 지출 상한이다. 이 한계는 두 방식 모두 명확히 표시해야 한다.

## 7. V는 도입하되 비교 범위를 고정한다

원안 V=Nb*ρr*(C-C')는 앞으로 작아진 입력을 반복해서 읽는 절약을 계상한다. 기존 v1은 이 이익을 인지했지만 코드에는 넣지 않았으므로, 이는 의미 있는 범위 확장이다.

다만 다음 조건이 필요하다.

1. Nb는 사용자 메시지 수가 아니라 비용이 발생하는 모델 입력 호출 수다.
2. B에 이미 포함한 복원 호출과 V의 호출 구간이 겹치면 안 된다.
3. 파킹 경로와 유지 경로의 동일한 작업 완료 구간을 비교한다.
4. 유지 경로가 도중에 예산 rollover를 할 경우 그 이후의 C-C' 절약을 계속 덧붙이지 않는다.
5. 파일 재읽기와 작업 진행으로 C'가 커질 수 있으므로 고정 45K는 가정이다.
6. 아직 복귀하지 않았으므로 V는 q와 함께 조건부 기대값으로 반영한다.

일반화하면 같은 작업 구간에서 모델 호출 j별 예상 문맥 차이를 합산한다.

```text
V ≈ E[Σ_j ρr_j*(C_raw_j - C_parked_j) | return]
```

다른 쓰기·출력·후속 handoff 차이도 있으면 동일 구간에서 함께 평가한다. V 때문에 실효 비용이 음수가 된다고 실제 quota가 환급되는 것은 아니다. 공통 미래 비용을 뺀 차액일 뿐이다.

### 7.1 즉시 파킹 N*의 전제

q=1, C>C', V의 구간이 중복되지 않고 원문 재개 읽기 A=a를 별도 계상했다면:

```text
N* = (G+B+Λ-a)/(ρr*(C-C'))
```

이는 주어진 단순화에서 성립한다. q<1인데 '복귀할 경우 N턴 한다'는 조건부 계획만으로 적용하면 안 된다. 복귀가 확정되지 않은 상태에서 추가 데우기 없이 warm 재개하는 이상적 기준 qa와 비교하면:

```text
N* = (G/q + B + Λ - a)/(ρr*(C-C'))   // q>0
```

이 역시 제한된 비교다. 유휴 중 아직 남은 무료 TTL, 종료 가능성, 즉시 사용자 복귀, 두 경로의 실제 작업량 차이를 포함하면 전체 기대비용을 사용한다.

### 7.2 Λ를 기존 rollover 예산에서 역산할 수 있는가

기존 예산 Cb가 경제적 최적 임계점이었다는 근거가 없으므로 이를 손실의 실측치로 해석할 수 없다. 하드 컨텍스트 한도, 실패 방지, 경험적 설정일 수도 있다. 역산값은 '이전 정책을 재현하도록 맞춘 보정 파라미터'라고 명시해야 한다.

또한 원안 (4)와 정확히 같은 비교식으로 역산한다면:

```text
Λ = Nbar*ρr*(Cb-C') - (G+B) + a
```

원안의 역산식에는 +a가 빠져 있다. 서로 다른 비용 기준을 쓰려면 그 차이를 설명해야 한다. 품질 손실을 근거 없이 설정해서 파킹 빈도를 억제하는 것은 비용 최적화 검증을 대신하지 않는다.

## 8. 복귀 분포와 운영 안전장치

### 8.1 관측 종료와 영구 미복귀를 구분한다

S(t)와 진짜 S(∞)가 주어졌다면 원안의 q(t), h(t) 식은 맞다. 그러나 관측이 끝날 때까지 돌아오지 않았다는 사실은 T=∞의 관측이 아니다. 이는 오른쪽 검열이다. [S1]

유한한 로그만으로 영구 미복귀율을 확정하려면 추가 가정이나 종료 정의가 필요하다. 진행 중 세션을 모두 ∞로 넣으면 긴 휴식 뒤 복귀할 사례를 미복귀로 잘못 분류할 수 있다. 기존 v1의 rightCensored와 neverReturnsProbability 구분을 유지한다.

### 8.2 K=C와 공유 캐시 생존

원문 재개와 파킹 복원 양쪽의 캐시 상태를 같은 시간축으로 평가한다. 공유 prefix가 항상 생존한다는 가정을 기본 사실로 두지 않는다. 반대로 파킹 부모 생성이 공유 prefix를 갱신하는 효과는 반영할 수 있다.

### 8.3 핑 실패와 캐시 사망은 같은 사건이 아니다

요청 거부는 기존 캐시를 곧바로 삭제했다는 의미가 아니다. cache_creation 증가가 확인된 성공 응답은 새 캐시가 방금 만들어졌다는 신호일 수 있다. 모델/lane 변화는 캐시 identity와 비용을 갱신할 이유이지 항상 같은 warm 파킹식을 실행할 이유가 아니다.

실제로 부모 캐시가 이미 사라졌다면 G를 warm 식으로 계산하면 안 된다. 첫 요청이 전체 재쓰기, 두 번째가 히트라면 G_cold≈K+(g-1)ρr C+ρo Oh다.

### 8.4 TTL 갱신 검증

공식 API 문서는 cache hit가 수명을 갱신하며, TTL은 요청 시작을 기준으로 한다고 설명한다. [A4] 다만 특정 OAuth 하네스가 같은 prefix와 TTL을 유지하는지는 별도 실험 대상이다.

예시 검증 설계: 다른 요청이 건드리지 않는 고유 prefix를 생성하고 t=0에 쓰기, t=55분에 ping, t=110분에 probe한다. 같은 길이의 별도 고유 prefix에는 ping을 하지 않는 대조군을 둔다. 요청별 TTL 설정, hit/write 토큰, quota 변화를 비교한다. probe도 캐시를 갱신하므로 중간 probe가 실험 조건을 바꾸지 않도록 한다. 캐시 최소 보존 이후의 우연한 생존을 배제하려면 반복·대조가 필요하다.

'갱신되지 않으면 항상 a=C'로 단정하지 않는다. 첫 ping은 hit일 수 있지만 유효 연장이 없을 수 있다. 비용과 생존 전이는 따로 측정한다.

## 9. 확장 반영 제안

| 항목 | 반영 방향 |
|---|---|
| 모델별 읽기/쓰기 quota | raw usage와 측정 근거를 보관한 모델·lane별 계수로 반영 |
| Fable 출력 계수 | 공식 가격 가정은 2.5. 실측 출력 계수가 확보되면 교체 |
| Rw/Rr 분할 | 현재는 추정. 실제 cache_creation/cache_read/modelOutput을 단계별 합산 |
| 미래 절약 V | 공통 작업 구간을 정의한 뒤 추가. 현재 복원 비용에 음수를 억지로 넣지 않음 |
| 품질 Λ | 기존 품질 게이트 유지. 별도 실패·재작업 근거로 보정 |
| 결정 엔진 | 기존 동적 계획법 유지. 원안의 고정 대안 h 규칙으로 대체하지 않음 |
| 무예측 정책 | q=1을 사실처럼 사용하지 않음. 승인된 지출 상한 또는 만료 |
| 경쟁비 보장 | 2배 보장 문구 제거 |
| 캐시 상태 | prefix/lane/요청 시작/쓰기·읽기를 기준으로 재평가 |

## 10. 이번 검증

기존 ZIP의 계산 엔진과 테스트를 별도 디렉터리에서 실행했다. 기존 30개 테스트는 통과했다. 새 반례는 독립적인 후방 계산과 기존 planIdle 모두 KEEP_WARM / 24.075K를 반환했다.

첨부 verify_comparison.cjs는 기본 산술, Fable 출력 보정, 감소 hazard, 원안 결정의 반례, 미복귀 2배 보장 반례를 검증한다. Node.js 표준 라이브러리만 사용하며, 기존 v1의 컴파일된 모듈 경로를 인자로 주면 해당 구현과도 대조한다.

```bash
node verify_comparison.cjs /path/to/rollover_policy_v1/dist/cache-policy.js
```

이 검증은 수식과 구현의 제한된 정합성만 확인한다. 사용자 실제 복귀 확률, quota 계수, 파킹 후 품질, 실제 절감률을 새롭게 측정한 것은 아니다.
