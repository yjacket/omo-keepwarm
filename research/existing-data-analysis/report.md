# 기존 자료로 본 유휴 정책의 미확정 항목 (오프라인 분석)

**요약.** 새 모델 호출과 대기 없이 로컬 자료만 다시 분석했다. 새로 알아낸 것은 네 가지다.

1. **q 후보 분포.** 사용자가 돌아올 확률 q는 rollover 확장 이벤트 로그로 "후보 분포"까지 추정할 수 있다. 입력 출처 라벨이 있는 2026-09-17~23 로그에서 진짜 유휴 구간 162개(세션 42개)를 얻었다. 누적 복귀율은 30분 0.58, 60분 0.65, 120분 0.72, 24시간 0.80이다.
2. **LET_EXPIRE 열세.** 이 후보 분포를 기존 DP에 넣으면, 캐시 만료 10분 전 판단 시점에서 모든 시나리오 90개 중 LET_EXPIRE가 한 번도 선택되지 않았다. 기대비용도 선택된 행동의 1.4~11배였다.
3. **PARK 차이의 조건.** 실험에서 잰 "파킹이 데우기보다 비싸다"는 차이에는 조건이 있다. 깨끗한 단위 4개에서는 파킹 후속 세션이 매 호출 대화를 통째로 다시 썼다. 후속 세션이 대화를 캐시에서 읽은 유일한 단위는 오염된 복원 2회차(참고용)였고, 여기서는 부호가 반대(파킹이 쌈)였다.
4. **확장 코드 결함.** 확장이 스스로 보내는 `/rollover now`가 shadow 기록에 "사용자 복귀"로 남는다. 이를 재현했다.

아직 알 수 없는 것도 네 가지다.

- **보정된 운영 예측.** 기간 간 차이가 커서 q를 보정된 운영 예측으로 올릴 수 없다.
- **계기 모형.** 계기가 사용량의 선형 함수이고 호출 단위로 늦게 반영된다는 모형은 재실험 245건 전체를 설명하지 못한다. 그래서 출력 계수는 여전히 측정값이 아니다.
- **실제 운영에서의 차이.** OMO의 실제 후속 세션에서 PARK와 KEEP_WARM의 차이는 모른다.
- **판단 기준.** 품질·지연 허용치는 자료로 정해지지 않는다.

기준은 `wt/idle-cost-shadow-implementation`의 `d8a4abd`다. 이번 작업에서 운영 설정, 정책, 코드, 커밋은 바꾸지 않았다.

## 2. q: 추정 가능성과 근거

**분석 단위.** 세션 전체가 아니라 유휴 구간을 단위로 삼았다.

**출처 A (rollover 이벤트 로그, 주 추정).** 정책이 실제로 쓰는 신호가 그대로 남아 있다.

- 유휴 시작: `agent_settled{total}`로 자식 작업 수를 알 수 있다. 값이 0일 때만 유휴 시작으로 봤다.
- 사용자 입력: `user_input{source}`로 사람의 입력과 확장이 주입한 입력을 구별한다.
- 세션 종료: `summary.jsonl`에 종료 사유(`quit`, `new`, `resume`, `reload`, `rollover`)가 남는다.
- 후속 세션: `rollover` 이벤트가 이어 주는 세션을 따라갔다. 유휴 파킹 뒤의 복귀는 후속 세션에서 측정했다.
- 확장 제거 뒤: 확장은 09-23 06:28Z 이후 설치돼 있지 않다. 그 뒤 같은 세션의 행방은 대화 기록으로 넘겨받았다.

**결과.**

| 결과 | 건수 |
|---|---|
| 복귀 | 120 |
| 맥락 종료 | 23 |
| 검열 | 19 |

복귀한 120건의 복귀 시간은 25%가 2.8분, 중앙값이 9.5분, 75%가 40분, 90%가 143분이다. 1일을 넘는 복귀도 있다. 두 건은 4.6일 뒤 `/resume`으로 같은 세션에 돌아왔다.

**민감도.**

| 조건 | 30분 | 60분 | 120분 |
|---|---|---|---|
| 기본 | 0.58 | 0.65 | 0.72 |
| 맥락 종료를 검열로 처리 | 0.61 | 0.69 | 0.77 |
| 맥락 ≥ 100K인 72개만 | 0.53 | 0.62 | 0.71 |
| 사용자가 친 `/rollover` 명령을 복귀로 봄(5개 구간) | 0.60 | 0.67 | 0.74 |

맥락 ≥ 100K에서는 5분 값만 0.13으로 크게 낮다.

**추정과 검증을 나눈 결과.** 대화 기록으로 P1에서 추정하고 P2에서 검증했다. 30~60분 복귀율이 약 0.12 낮아졌고 구간도 거의 겹치지 않는다. P3(자율 실행과 실험 런처 기간)은 검열이 67%(대부분 자동 재개)이고 30분 뒤 관측 중인 구간이 9개뿐이다. 즉 복귀 분포는 작업 방식(대화형 대 자율 실행)과 기간에 따라 달라진다. **이 자료로는 "보정된 운영 예측"을 만들 수 없고, 조건부 후보 분포만 만들 수 있다.**

**식별 불가 항목과 이유.**

| 식별할 수 없는 것 | 없는 필드 또는 대조 |
|---|---|
| 영구 미복귀 비율 | 24시간 뒤 관측 중인 구간이 4개다. 작업 종료 신호(`observeTaskEnd`)가 호스트에 연결돼 있지 않다 |
| 맥락 종료가 작업 완료인지 포기인지 | 종료 이유 필드가 없다 |
| 새 세션에서 같은 작업을 이어 간 경우 | 세션 사이에 작업 식별자가 없다 |
| 09-23 이후 기간 | 입력 출처 라벨이 없다. 확장이 설치돼 있지 않다 |

## 3. 오프라인 정책 재생 (기존 DP 그대로)

**설정.** `planIdle`(extension/rollover.ts, d8a4abd)을 고치지 않고 불렀다.

- 비용 모델: `docs/idle-live-results.json`의 계수 범위 양 끝(low, high) 모형이다. 분석기의 변환 함수로 다시 만들어 저장된 값과 같음을 확인했다.
- 재검토 간격: 50분이다.
- 캐시 수명: 1시간이다.
- 인수인계 손실·스킬 복원·품질 비용: 0 기준값이다(측정 안 됨).

**q 후보 5개.**

- A 기본
- A에서 맥락 종료를 검열로 처리
- A에서 맥락 ≥ 100K만
- A에서 사용자가 친 명령을 복귀로 봄
- B의 P1

**관측 지평과 꼬리 배분.** 관측 지평은 전체, 24시간, 4시간 세 가지다. 지평 밖의 남은 확률은 가정으로 명시하고 세 방식으로 나눴다.

- 영구 미복귀
- 관측 끝 직후 복귀
- 72시간 뒤 복귀

**재생 결과.**

- **유휴 시작 시점:** 45/45가 WAIT다. 캐시가 아직 공짜로 살아 있으니 지금 돈을 쓰지 않는다.
- **50분 시점의 조건:** 50분까지 복귀하지 않은 비율은 21~38%다. 맥락 종료는 시각 없이 영구 미복귀로 넣었으므로 보수적인 값이다. 그중 다음 1시간 안에 복귀할 확률은 0.23~0.30이다.
- **50분 시점의 선택:** 파킹을 허용하면 PARK 40, 판정 불가 5다. 판정 불가는 범위 양 끝의 선택이 갈린 경우이고, 모두 4시간 지평 시나리오에서 나왔다. 파킹을 허용하지 않으면 KEEP_WARM 45다. LET_EXPIRE의 기대비용은 선택된 행동의 1.4~11배다. 가장 작은 1.4배는 파킹 불허 조건에서, 4시간 뒤 남은 확률을 모두 72시간 뒤 복귀로 둔 가정이다. 이때 데우기를 오래 이어 가야 한다.
- **독립 산술:** Python으로 따로 셈했다. 50분에 열려 있는 구간이 결국 복귀할 확률은 0.70이다. 데우기 한 번의 비용은 차가운 재작성 비용의 0.025~0.027배다. 만료 방치가 이기려면 결국 복귀할 확률이 대략 0.1보다 작아야 한다. 관측값은 그 여러 배라서, LET_EXPIRE 열세는 q의 불확실성 안에서 유지된다.
- **PARK와 KEEP_WARM 사이의 선택은 조건부다.** 두 기대비용의 차이는 −14%~+30%로 얇고 부호도 바뀐다. 미래 작업 차이 V에 따라 바뀐다(V는 원문 경로 본작업 비용 빼기 파킹 경로 본작업 비용, 양수면 파킹이 유리).

| V 시나리오 | 50분 시점 결과 |
|---|---|
| V = 0 | PARK |
| V = 복원 1회차 실측(후속 세션이 매번 다시 씀: low −0.00126, high −0.00190) | 판정 불가(low PARK, high KEEP_WARM) |
| V = 후속 세션이 대화를 캐시에 둔다는 가정(low +0.00144, high +0.00114) | PARK |

출력 계수를 모형 조건부 범위(3.13e-5~3.48e-5 tick/토큰)로 바꿔도 V = 0에서 PARK다.

**재생 결과를 읽을 때.** 이 결과는 로그 추정 q, 실측 단계 비용, 가정 꼬리를 섞은 계산이다. 세 정책을 실제로 대조한 결과가 아니다. 실제 엔진(`evaluateIdleCost`)은 추가 조건도 본다. 다섯 승인 설정이 모두 `unconfigured`라 선제 지출(데우기 핑, 파킹 생성) 자체가 막히고, 예측도 "보정됨"이 아니다. 따라서 지금의 운영 판단은 그대로다. **이 재생으로 확인한 것은 "q 후보가 이 정도라면 만료 방치 기본값은 비용상 가장 불리하다"는 조건부 사실이다.** 세 정책 중 무엇이 최적인지는 확정하지 않았다.

## 4. 기존 실험 자료의 재분석에서 새로 구분한 점

### 4.1 계기 지연과 출력 계수

**방법.** 계기를 `floor(위상 + 보이는 호출들의 선형 비용)`으로 놓고, 위상을 정확한 구간으로 풀었다. 그 위에서 (읽기 계수 R, 1시간 쓰기 계수 T, 출력 가중 w)를 전수 스캔했다. 보이는 호출의 범위는 두 방식으로 정의했다.

- 호출 지연 L: 헤더가 i−L번째 호출까지 반영한다.
- 시간 지연 d: 헤더가 d초 전에 끝난 호출까지 반영한다.

Node와 Python 두 구현의 결과가 같다.

**결과.**

- **첫 실행 22건.** 기존 D1 결과를 격자까지 그대로 재현했다. 지연 0과 지연 2는 불가능하다. 지연 1은 T 80.5K~89.5K, w 1.559~10.457에서만 가능하다.
- **재실행 245건 전체(한 창).** 어떤 모형도 전부를 설명하지 못한다.

| 모형 | 맞는 최대 접두부 | 처음 깨지는 호출 |
|---|---|---|
| 지연 0 | 11건 | 복원 park_path/8 |
| 지연 1 | 176건 | policy-effect/current_policy/44 |
| 지연 2 | 40건(R 범위를 넓히면 64건) | fable-write-tick |
| 시간 지연 5초 | 94건 | - |
| 시간 지연 15초 | 88건 | - |
| 시간 지연 30초, 60초 | 4건 | - |
| 시간 지연 120초 | 11건 | - |

- **지연 0의 직접 반례.** 146.4K토큰의 1시간 쓰기는 측정된 T 기준으로 1.1 tick 이상이다. 그런데 이런 호출 5/5가 자기 헤더를 움직이지 않았고, 20.5초 뒤의 다음 호출 헤더가 +1 또는 +2 움직였다.
- **지연 1이 176건까지 맞으려면.** 읽기 계수 R이 09-19 사전 범위(5.39M~5.55M)의 위 끝 한 격자점(5.55M)이거나, 그 범위를 조금 벗어난 5.61M~5.99M이어야 한다.
- **출력 실험 구간(42건)만 보면.** 지연 0, 1, 2 모두 맞는다. 출력 토큰당 tick은 지연 0에서 3.33e-5~3.48e-5, 지연 1에서 3.23e-5~3.40e-5, 지연 2에서 3.13e-5~3.25e-5다. 기존의 "블록 1과 2가 겹치지 않음"은 블록 1의 위상을 기계가 기록한 이월 위상으로 고정할 때만 생긴다. 이월 위상은 앞 구간 경계에서 지연 0을 가정한 값이다.

**해석.** 출력 계수는 "선형 floor 모형 + 호출 지연 0~2 + 읽기 사전값"이라는 조건 아래서만 3.1e-5~3.5e-5 tick/토큰이다. 1시간 쓰기 토큰 대비 약 3.7~4.6배로, 엔진의 사전 비율 0.5~2.5배보다 크다. 여러 모형이 같은 자료에 맞으므로 이 값을 측정 계수로 올리지 않았다. 게시값은 기존 상한 `4.096952e-5`를 유지한다. policy-effect 구간은 어떤 지연으로도 맞지 않는다. 따라서 "사용량의 선형 함수"라는 환산 가정 자체가 긴 무활동 뒤 연속 읽기 구간에서는 검증되지 않았다. 다만 정책 쌍의 비용 차이는 계기가 아니라 사용량에 계수를 곱해 낸 값이라 이 불일치에 직접 영향받지 않는다.

### 4.3 확장 코드 결함 (결과를 바꿈, 수정 제안만)

**현상.** 파킹이나 예산 rollover가 착지할 때 `tryRollover`가 `pi.sendUserMessage("/rollover now")`로 명령을 스스로 보낸다. 이 명령은 사용자가 친 명령과 같은 핸들러를 타고, 핸들러는 세 가지를 한다.

- `shadowClose("returned", "command")`로 유휴 shadow 에피소드를 "복귀"로 닫는다.
- 사용자 시계 `lastUserAt`을 옮긴다.
- `command{verb:"now"}`를 기록한다.

**근거.**

- 코드 위치: `extension/rollover.ts`의 `tryRollover`와 `registerCommand("rollover")` 핸들러.
- 운영 로그: `successor_found` 직후의 `now` 명령이 29건이다.
- 재현: `scripts/repro-self-dispatch-shadow.mjs`. 가짜 호스트에서 사람의 입력 0건인데 마지막 shadow 기록이 `episodeStatus: "returned"`, `episodeEndReason: "command"`였다(`defectReproduced: true`).

**영향.** shadow 기록을 q 보정용 일상 관측 자료로 쓰면 rollover가 착지할 때마다 가짜 복귀가 들어간다. 이 분석에서는 그 명령을 사용자 입력에서 뺐다.

**수정 제안.**

- `tryRollover`에서 자기 발송 표지를 세운다.
- 핸들러는 그 표지가 있으면 shadow를 "복귀"가 아니라 `right_censored`(사유 `self_rollover`)로 닫고 `lastUserAt`을 옮기지 않는다.
- 회귀 테스트: 유휴 파킹 → successor → 자기 발송 now → 에피소드가 `returned`가 아님.

운영 코드는 고치지 않았다.

## 5. 후속 항목

- self-dispatch 결함의 재현.

### 추가 모델 호출 없는 일상 관측만 필요

**q의 보정.** 입력 출처 라벨이 있는 로그를 몇 주 더 모아야 한다. 최소 필드는 다음과 같다.

- 유휴 시작 시각과 자식 작업 수
- goal/자율 여부
- 입력 출처(사람 / rpc / 확장 / 자기 발송 명령)
- 세션 종료 사유
- 후속 세션 연결
- 맥락 크기
- 작업 종료 신호
- 실험·런처 표지

수집 방법은 둘 중 하나다.

- (a) rollover 확장을 다시 설치하면 이벤트 로그가 이 필드 대부분을 남긴다.
- (b) self-dispatch 결함을 고친 뒤 `idleCostMode: "shadow"`를 켠다.

둘 다 모델을 호출하지 않지만 설치나 설정 변경이라서 사용자 승인이 필요하다. 이번에는 켜지 않았다.

**수집 뒤의 검증.** 기간을 나눠 앞 기간으로 추정하고 뒤 기간으로 검증한다. 대화형과 자율 실행을 나눠 층별로 추정한다.

**운영 OMO의 PARK 비용.** 실제 파킹 뒤 후속 세션의 캐시 적중과 부모 인수인계 생성 비용은 사용량 기록만으로 계속 관측할 수 있다. 이미 5개 세션이 있다.

### 사용자가 정할 운영 기준

1. **다섯 승인 설정.** `maxProactiveSpendPerIdle`, `maxTotalExperimentalSpend`, `maxResumeDelay`(CLI 실험에서 파킹 복원은 약 19초 더 걸렸다), `allowedQualityDegradation`(재설명 요청 5/5를 허용할지), `minimumEvidenceForEnforcement`(예: 기간을 나눈 검증을 통과한 q가 몇 주 필요한지).
2. **복귀와 종료의 정의.** 사람이 친 `/rollover`·`/resume`을 복귀로 볼지, 세션을 닫고 새로 연 것을 맥락 종료로 볼지.
3. **파킹 허용 여부.** 비용이 아니라 품질·지연 조건으로 정한다.
4. **수집 방식.** 확장을 재설치할지 shadow를 켤지, 결함을 먼저 고칠지.
